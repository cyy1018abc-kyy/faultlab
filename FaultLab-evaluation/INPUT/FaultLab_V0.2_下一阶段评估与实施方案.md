## 0. 决策摘要：先让两位智能体评审什么？

**结论建议**：项目有可做的 MVP 切口，但最容易失败的原因不是前端 UI，而是 **“好看的演示”误导用户认为是已验证的物理仿真**。首次公开应明确 L0 解析/行为级演示，不宣称工业真实性；优先保障可回放、可对照、可追溯、可解释，而不是增加模型数量、3D、LLM 或账户系统。

### 0.1 建议立即执行的事情（只评估，不编码）

3. 每个评审者分别给出 `保留 / 修改 / 删除 / 推迟` 四类建议，并给出可检验的判据。
4. 汇总分歧，明确决策者裁定；仅在 G0（评审门）通过后进入页面原型与技术验证。
5. **不得直接推送代码、创建真实 GitHub 仓库、联网部署或读取/复制 SpaceFDIR 私有资产**，除非后续单独授权。

## 1. 对上游 V0.1 文档的审阅边界与已识别核查点

### 1.1 保持不变的产品事实

- FL-001：发电机—电池—理想 400 V 直流母线—30 kW 负载。
- 仿真时长 60 s；故障在 `t_f=20 s` 激活；传感器正偏置 `b=+10 A`；正常电池电流 25 A。
- 理想功率关系：`P_gen,true + P_bat,true = P_load,served`，在本例 `P_load,served = P_load,demand = 30 kW`。
- 观察三层概念：`MODEL_STATE`（真实状态）、`OBSERVATION`（测量）、`DERIVED/INFERENCE`（派生或推断）。
- 五种逻辑页面：实验首页、系统交互图、实时曲线、因果解释、结果对比。
- 不支持任意 `.slx` 文件上传即执行，不控制真实设备。

### 1.2 必审的文档问题

**R-01：不连续事件时刻。** `t=20−` 与 `t=20+` 是同一物理时刻的两个事件相位。`I_true(20−)=I_true(20+)=25 A`，但 `I_meas(20−)=25 A`、`I_meas(20+)=35 A`。只用一个 `time_s=20.0` 的普通浮点采样行，会丢失其中一个观测状态。**建议单独存 `event_snapshots` 的 pre/post**，常规采样网格默认取 post，图表以阶跃图绘制，数据导出同时携带事件文件。

**R-02：行为级模型的声明。** 等效一阶微分方程表达的是“假设的闭环行为”，不是从实际电机、电力电子和母线电容方程推导出的完整模型。发电机在本模型中是瞬时平衡补偿源，**绝不能呈现虚构的发电机滞后曲线、频率波动、电压尖峰或设备保护动作**。

**R-03：反馈与监测边界。** 「闭环反馈」和「仅监测」要分别运行并保留各自 `run_id`。在「仅监测」里 `I_true=25 A` 保持不变、`I_meas=35 A`；测量残差 +4 kW 仍成立，不能因为控制不受影响就把传感器故障隐藏。

**R-04：SOC 估计值定义。** 以故障电流积分得到的是示例**库仑计数估计值**，并不代表所有现实 BMS 对 SOC 的估计逻辑。报告字段需写明 `estimator_method=naive_coulomb_counting` 与 `SOC_est - SOC_true` 的**百分点 pp**单位。

**R-05：负载需求 vs 已服务负载。** 本例二者同为 30 kW；数据契约必须将其分开，否则扩展未供电/供电不足案例时会不兼容。

**R-06：验证与真实的区别。** 检查 `max|r_true|≈0` 和解析解一致，只证明**模型内部一致性**；不能证明其与真实设备一致。需要区分 `consistency_check_passed`、`model_validated_against_experiment`、`real_hardware_verified` 等不同证据等级，后两者在 V0.1 只能是 `not_performed`。

**R-07：运行快照的真实性。** 前端在浏览器计算出的 `SHA-256` 仅可证明导出后的内容一致性，**不等于防篡改签名或第三方认证**。除非引入受信服务器、签名及审计策略，不能称之为 sealed 或第三方独立验证。

**R-08：P0/P1 范围冲突。** 上游文本将“仅监测模式”放在 P1，但因果讲解高度依赖它；需要评审决定是否提升 P0。建议明确 P0 是「固定参数的基准/闭环/仅监测 3 组可复现运行」，把自由修改参数推迟到 P1。

## 2. 产品交付目标、用户旅程和成功标准

### 2.1 面向谁？

| Persona | 核心目标 | 对应主路径 |
|---|---|---|
| 初次接触故障诊断的学生 | 理解“传感器错”不等于“物理量直接错” | 首页 → 系统 → 第20秒 → 曲线 → 解释 |
| 控制与能源研究者 | 核对方程、变量意义、功率与电能积分 | 系统 → 数据检查器 → 对照 → CSV/配置 |
| AI/开源开发者 | 复用最小运行、数据与事件协议 | 文档 → 演示 → 读取示例 Run → 自动化验证 |

### 2.2 首次体验主旅程（参考，而非强制线性）

1. **首页**：看到一句话问题、场景、模型限制；点击「进入实验」。
2. **系统页 0–19.9s**：发电 20kW + 电池 10kW = 负载 30kW；点击电池或传感器核对变量。
3. **故障事件 20s**：观测电流 post 突升 10A，真实电流连续；系统展示非阻断的解释提示。
4. **20–60s**：回放真实电池电流下降、理想平衡源补偿；曲线、拓扑、时间线联动。
5. **因果页**：点击每条关系，关联具体 `run_id + signal + time/event phase` 数据证据。
6. **结果对比**：与无故障组叠加，再与「仅监测」组比较；查看原始数据和报告可信度说明。
7. **导出**：下载 `manifest + timeseries + events + metrics + checks`，能在离线环境复核。

### 2.3 核心成功标准（评审通过后可调整）

- 能在无 MATLAB 环境下完成上面全流程，且无需注册、秘钥或外部 API。
- 模型计算不依赖播放速度：暂停、加速、切页、拖动游标、重复回放不改变运行数据。
- 图表在 20s 不抹平跳变，完整说明 pre/post。
- 真实与测量信号的标签、单位、线型一致；任何数据卡片可以回溯来源。
- 三组运行（无故障、闭环故障、仅监测故障）都可重放、比较、导出。
- 质量检查失败不显示「验证通过」，异常状态可阅读、可复查。

## 4. 建议的技术架构（待 Codex/Claude 论证）

### 4.1 架构约束

- 首版**本地可运行、无外部依赖服务**；不强依赖 MATLAB/Simulink、云端数据库或模型 API。
- 物理引擎是**纯函数/无副作用的计算单元**：输入确定的配置，输出确定的不可变运行数据。
- 物理/事件/指标计算与 UI 视觉组件解耦；播放只读取数据，不重新求解。
- 未来适配 Python、Simulink/FMUs 是一种**协议适配**，不是强迫 V0.1 引入后端。
- G0 先选择架构，不应由于熟悉某个框架而直接定案。

### 4.2 三个可行选项

| 方案 | 结构 | 优点 | 风险/代价 | 建议 |
|---|---|---|---|---|
| **A 纯浏览器** | React/Vite/TypeScript + 浏览器本地计算 + JSON/CSV 导出 | 一键打开、静态托管、无后端运行成本 | 数值内核需严格测试；未来服务端运行另行适配 | **V0.1 首选** |
| **B Python API + Web** | FastAPI 数值服务 + React UI | 与科研 Python/后续求解器衔接直接 | 开发、部署、日志和跨进程状态更复杂 | 作为 L1 候选 |
| **C 全 Python UI** | Python 仿真 + Streamlit/Gradio 类界面 | 原型快，单栈维护 | 拓扑图与时间线的精细交互受限，面向公众的前端体验不一定理想 | 内部验证备选 |

**推荐架构 A，但必须设立“独立数值预言机”**：可用数学闭式解与一套独立的 Python 检查脚本或外部参考表对浏览器计算结果交叉核对。不能仅以同一段 TypeScript 代码计算并自我断言作为物理验证。

### 4.3 V0.1 建议组件边界

```text
应用壳 AppShell
 ├── 实验目录 ExperimentCatalog / 引导 Home
 ├── 配置草稿 ScenarioEditor          ──> Config Schema
 ├── 运行管理 RunRegistry             ──> immutable RunManifest
 ├── FL-001 数值内核 ModelEngine      ──> raw Signals + Events
 ├── 检查/积分 Metrics & Validators   ──> Checks + Derived Metrics
 ├── 共享时间线 PlaybackClock          ──> view-only timestamp
 ├── 系统视图 SystemCanvas            ──> signal bindings
 ├── 曲线 SignalsView                 ──> raw signals, event snapshots
 ├── 因果视图 CausalExplorer          ──> model rules + evidence links
 ├── 对照视图 CompareView             ──> immutable paired runs
 └── 导出与重载 EvidenceExporter      ──> manifest, raw data, event log
```

**重要责任边界**：

- `ModelEngine` 不输出“故障严重”“诊断成功”之类主观文案。
- `CausalExplorer` 不对模型没有定义的物理过程做确定性解释。
- `PlaybackClock` 不改变 `Run` 的哈希、数据点或求解步长。
- `CompareView` 只计算同语义、同单位、兼容时间基准的差值。
- `EvidenceExporter` 不读取屏幕当前显示值来组装科学数据，而从运行数据源导出。

### 4.4 建议但不锁定的工具

- UI：**React + TypeScript + Vite**；状态可先用小型集中 store/上下文，不为了 5 页引入复杂全局框架。
- 曲线：**Apache ECharts**（交互缩放、多序列、事件线、SVG/Canvas）；重点验证**阶跃点、游标同步、键盘访问、CSV 源数据**，不能只看效果图。
- 系统拓扑：V0.1 固定少量节点优先**手工 SVG + 数据绑定**；不宜一开始增加复杂自动布局图引擎。
- 测试：数值单元测试 + **Playwright** 真实浏览器端到端测试；优先覆盖边界与跨页状态。
- Schema：JSON Schema 或类型定义 + 运行时校验；配合版本化迁移策略，避免只有 TypeScript 类型而没有导入检查。
- 哈希：规范化序列化后计算 SHA-256；记录 Hash 口径、字段排序、浮点序列化规则。**不暗示第三方认证**。
- FMI/FMU：只在长期接口预留。FMI 3.0 官方把 Model Exchange / Co-Simulation / Scheduled Execution 明确区分，V0.1 不声明已实现任何 FMU 执行能力。

## 5. FL-001 物理内核：模型定义和数值金标准

### 5.1 固定参数

| 字段 | 值 | 单位/语义 |
|---|---:|---|
| `duration_s` | 60 | 秒，范围 [0,60] |
| `sample_dt_s` | 0.1 | 秒，均匀记录点 601 个 |
| `fault_time_s` | 20 | 秒，独立事件 pre/post |
| `bias_A` | 10 | A，传感器测量偏置 |
| `Vdc_V` | 400 | V，理想恒压，不进行电压动态求解 |
| `Iref_A` | 25 | A，放电为正 |
| `tau_s` | 1.5 | 秒，闭环行为级一阶时间常数 |
| `Pload_demand_kW` | 30 | kW，恒定；已服务负载本例相同 |
| `Ebat_nominal_kWh` | 40 | kWh，理想容量 |
| `SOC0_pct` | 60 | %，初值 |

### 5.2 解析方程

`b(t)=0` 当 `t<20`，当 `t>=20` 为 10A。以电池**放电为正**：

- `I_meas(t) = I_true(t) + b(t)`。
- **闭环** `t<20`：`I_true=25`；`t>=20`：`I_true=15+10*exp(-(t-20)/1.5)` A。
- **仅监测**：全程 `I_true=25 A`，只有 `I_meas` 自 20s 后变为 35A。
- `P_bat,true = Vdc*I_true/1000 = 0.4 I_true` kW。
- `P_bat,meas = 0.4 I_meas` kW（仅是按错测量换算的显示量）。
- `P_gen,true = P_load,served - P_bat,true` kW，**理想平衡源**。
- `r_true = P_gen,true + P_bat,true - P_load,served = 0` kW。
- `r_meas = P_gen,true + P_bat,meas - P_load,served = 4` kW（20s 后）。
- `SOC_true(t) = 60 - 100 * (1/40) * ∫[0,t] P_bat,true(s)/3600 ds` %。
- `SOC_est(t)` 用 `P_bat,meas` 积分，**仅代表理想化库仑计数估计**。

**适用边界**：实际发电机控制时滞、变流器开关动态、母线电容、电化学 OCV/温度、效率损耗、传感器采样噪声、保护逻辑均未建模。不得显示这些未计算的物理效应。

### 5.3 黄金样例（由独立参考计算再次核定）

| 场景/时刻 | 真实电流 A | 测量电流 A | 电池功率 kW | 发电功率 kW | 测量残差 kW |
|---|---:|---:|---:|---:|---:|
| 正常 `t=19.9s` | 25 | 25 | 10 | 20 | 0 |
| 闭环 `t=20s` post | 25 | 35 | 10 | 20 | +4 |
| 闭环 `t=21.5s` | 18.6788 | 28.6788 | 7.4715 | 22.5285 | +4 |
| 闭环 `t=26s` | 15.1832 | 25.1832 | 6.0733 | 23.9267 | +4 |
| 闭环 `t=60s` | ≈15 | ≈25 | ≈6 | ≈24 | +4 |
| 仅监测 `t=60s` | 25 | 35 | 10 | 20 | +4 |

全程负载电能 `30*60/3600=0.500000 kWh`。闭环故障：电池电能约 `0.123889 kWh`，发电电能约 `0.376111 kWh`，真实 SOC 末值约 `59.69028%`；SOC 估计减去真实值为 `-0.111111` **百分点**。无故障和仅监测的真实电池电能均为 `0.166667 kWh`，发电电能 `0.333333 kWh`，真实 SOC 末值 `59.583333%`；仅监测的估计 SOC 同样受到偏置影响。

以上是待自动化固化的**解析金标准**，不是现场实测值；在 G2 应对计算脚本进行独立复核。

### 5.4 事件前/后表达约定

- 常规时钟：`0.0,0.1,…,60.0 s` 共 601 个**常规采样点**，20.0s 行作为 `post`。
- 事件记录：`fault_triggered`、`t=20.0`、`phase=pre/post`，记录真实/测量电流与配置差异。
- `20−` 是左极限，不意味着时间 `19.9s`；即使曲线上含 19.9s 采样值，也要区分事件左极限和上一个采样点。
- 只对连续的真实状态进行合法插值；观测阶跃必须显示跳变，禁止跨故障瞬间样条平滑。
- 日后支持动态更复杂模型时，要明确求解器的事件定位策略和积分步长、输出采样步长不同的含义。

### 5.5 主要校验（G2 的最低门槛）

| 检查 | 通过条件（建议） |
|---|---|
| `PHY-01` 真实功率平衡 | max abs `r_true` ≤ 1e-9 kW（仅 L0 解析模型） |
| `PHY-02` 偏置约束 | pre `I_meas-I_true=0`；post `=10A`，浮点误差容限 |
| `PHY-03` 连续状态 | `I_true(20−)=I_true(20+)` |
| `PHY-04` 闭环趋势 | 20–60s 真实电流从25A单调趋向15A，正偏置下无虚假越界 |
| `PHY-05` 仅监测 | 真实电流全程25A，测量信号只在20s后偏置 |
| `PHY-06` 能量积分 | E_gen + E_bat = E_served=0.5kWh，在一致积分规则/容差下通过 |
| `PHY-07` SOC | 使用秒→小时换算；`SOC_est-SOC_true=-0.111111pp` (60s) |
| `PHY-08` 非回归 | 改变播放速度、页面、游标不会改变 Run 数据与哈希 |
| `PHY-09` 配置变化 | 新参数生成新 Run；旧 Run 的完整内容与 ID 保持不变 |
| `PHY-10` 数据完整性 | 单位、时钟、变量长度、事件引用、有限浮点值检查全部通过 |

备注：如果 L1 使用数值积分器，应重新规定对等的误差准则，**不能机械套用解析计算 1e-9 kW 容差**。

## 6. 产品数据契约 V0.1（建议最小集合）

### 6.1 核心对象

| 对象 | 必需字段 | 生成者 | 消费者 |
|---|---|---|---|
| `ScenarioConfig` | schema_version, model_id, duration_s, sample_dt_s, fault_time_s, bias_A, feedback_mode, initial_SOC_pct | 配置编辑器 | ModelEngine |
| `ModelManifest` | model_id/version, equation_id, unit_system, assumptions, limits, engine_compatibility | 模型资源 | 首页/解释/校验 |
| `RunManifest` | run_id, config_hash, model_hash, engine_version, schema_version, created_at, status, provenance_tier | RunRegistry | 所有页面/导出 |
| `SignalCatalog` | signal_id, name, unit, source_kind, description, equation_ref | 模型与字段字典 | 检查器/图表 |
| `TimeSeries` | time_s + 逐变量列，排序且时间单调，含 meta 引用 | ModelEngine | 图表/指标/导出 |
| `EventSnapshot` | event_id, time_s, phase(pre/post), signal_values, fault_id | EventEngine | 事件回放/图表 |
| `QualityChecks` | check_id, status(pass/fail/skipped), observed, tolerance, reason | Validators | 导出/质量标签 |
| `EvidenceLink` | run_id, signal_id, event_id或时间区间, rule_id | 因果规则层 | 因果面板/报告 |
| `ComparisonResult` | baseline_run_id, fault_run_id, compatibility, aligned_signals, differences | CompareEngine | 对比页面 |

建议 `source_kind` 取值：`CONFIG`, `MODEL_STATE`, `OBSERVATION`, `CONTROLLER`, `FAULT_EVENT`, `DERIVED`, `MODEL_ASSUMPTION`。另增 `provenance_tier` 表示 `analytical_demo`，未来另有 `numerical_simulation`、`hardware_experiment`，不允许由 UI 随意切换。

### 6.2 不可变运行原则

1. Run 的**内容不可变**；可改变的是独立存储的回放位置、图表显示设置和当前选中对象。
2. `Config` 正规化后生成 `config_hash`；运行结果与 `engine_version`、`model_hash` 同时绑定。
3. 数据导出包含原始表、事件文件、模型与配置快照、指标与检查结果；报告只引用这些源数据。
4. 用户修改参数后状态标记 `draft_dirty`，必须主动点击「创建新运行」。
5. 并发时不同 Run 用唯一身份隔离；不能以全局可变数组覆盖当前显示数据。
6. 浏览器存储不是可靠的科学归档，刷新或清理缓存可能丢失实验；必须提供明确的**下载导出**。

### 6.3 最小证据包目录建议

```text
FL-001-RUN-xxxx/
  manifest.json              # 数据和引擎身份、来源等级
  config.json                # 已运行的规范化配置
  model_manifest.json        # 方程版本、单位、假设和限制
  timeseries.csv             # 所有原始采样点，含单位字典引用
  events.json                # 故障事件与 pre/post 快照
  metrics.json               # 可复查的积分指标
  checks.json                # 校验状态与具体误差
  SHA256SUMS.txt             # 文件级校验和，非第三方签名
  report.html                # P1 可选，不作为唯一证据
```

**真实性规则**：对于未通过检查的 Run，可输出**带 FAIL 标签的排障证据**，但不允许输出“验证通过”标记。

## 7. 页面与交互的下一阶段高保真设计任务

### 7.1 共用设计系统

- 保持清晰的视觉语言：**物理功率流**用实线箭头；**传感器观测/控制指令**用不同虚线或标记；**故障事件**用可解释的独立事件符号。

## 9. 测试矩阵：数字正确不够，还要行为正确

### 9.1 数值与物理测试

- 20−/20+ 突变；21.5/26/60s 黄金时刻。
- 真实电池/发电/负载功率关系及电能积分。
- 无故障、闭环故障、仅监测故障三组结果。
- SOC 估计误差的符号与 **pp vs %** 标签。
- dt 从 0.1s 改变时输出采样与积分机制的正确性（若 P1 开放 dt，要求重建金标准）。
- 非法参数、空信号、NaN、Infinity、时间无序、单位不匹配、损坏的导入文件。

### 9.2 UI/交互测试

- 进入首页 → 系统 → 20s → 曲线 → 因果 → 对照 → 导出。
- 页面切换保留选中对象、游标、显示偏好、当前 Run。
- 参数草稿 dirty 后原 Run 不变，创建新 Run 后可以返回旧 Run。
- 改变播放倍速/暂停/重复/拖动不改变数值轨迹。
- 20s 事件以符号/线型表达，不能被平滑图表误呈现。
- 键盘可操作、焦点顺序清晰、图表有文本/表格替代、可关闭动效。

### 9.3 可信导出与失败路径测试

- 同一个 Run 的原始数据导出后再导入，哈希核对、指标一致。
- 篡改 CSV 数据一行，完整性检查应失败；但不得宣称可抵御故意伪造完整重新签名的攻击。
- `quality_checks=failed` 时报告醒目显示未通过，不可贴可信认证。
- 对照 Run 模型版本/初始条件/单位不兼容时禁止“仅由故障造成”类因果断言。
- 浏览器刷新、导出文件丢失、本地缓存不可用时有明确降级与提示。

### 9.4 手动产品走查

- 初学者能否在不阅读长文档的情况下区分“真实”和“测量”？
- 研究人员能否查到每个关键数字的公式/单位/来源？
- 评审者能否指出所有演示模型未覆盖的物理过程？
- 工具运行失败时，页面是否明确告诉用户当前没有可信结果？

## 15. 统一评分标准与双评审合并机制

### 15.1 评分

按每项 **1（明显不足）—5（可直接推进）** 评分，附至少一句证据：

| 维度 | 权重 | 重点 |
|---|---:|---|
| 物理正确与模型边界 | 25% | 方程、单位、误导风险、故障机制 |
| 数据语义与追溯 | 20% | 真值/观测/推断分离、Run、证据 |
| 用户体验与清晰度 | 15% | 五页面、关键互动、认知负担 |
| 实施可行性 | 15% | 独立开源、静态离线、工程成本 |
| 自动化验收 | 10% | golden、事件、数值/浏览器回归 |
| 开源合规与安全 | 10% | 私有资产、许可证、范围约束 |
| 演进扩展性 | 5% | 新模型、Python、Simulink、Agent接口 |

**评分不能平均掉 P0 物理错误**。即使综合得分高，只要出现证据造假、严重物理错误、私有资产泄漏或 Run 不可追溯等阻断问题，结论必须为 `NO-GO` 或 `CONDITIONAL GO`。

### 15.2 合并流程

1. 收齐两个独立报告，按问题 ID 对齐，不只比较总分。
2. 建立 `REVIEW_DIFF.md`：`问题 → Codex 观点 → Claude 观点 → 证据 → 决策者裁定 → 后续任务ID`。
3. 对冲突问题做最小验证：必要时独立手算、参考脚本、页面线框 A/B 走查；不要以模型声量/写作长度裁定真伪。
4. 把认可的调整写入 `DECISIONS.md`，每条包含理由、替代选项、后悔成本和撤回条件。
5. 冻结 `SPEC_v0.2_APPROVED.md` 后才向实现 Agent 下发建仓与编码任务。

### 15.3 评审必须产出的最终问题清单

- “V0.1 最小可发布闭环”到底包含哪些功能？
- 纯浏览器方案是否满足教学目标且物理结果可复核？
- 20 秒事件如何同时表达 20−/20+ ？
- 无故障/闭环/监测三组结果如何保障完整且可比较？
- 哪些页面允许看到物理真值、哪些未来必须隔离？
- 数值通过/模型验证/实测验证如何严格区分？
- 公开仓库中绝对不能出现哪些文件与依赖？
- 什么失败测试会阻止打包发布？

## 17. 评审后建议的实际执行顺序

**先做的三件**：

1. 用双评审确认模型是正确、清晰且不会误导用户的；确定 P0/P1 及前端架构。
2. 首先锁定**模型/事件/Run 数据契约**与黄金样例；其后再绑定页面实时交互，以免为了 UI 改变科学数据意义。
3. 基于冻结数据字典，完成五页面可点击高保真原型，重点验证 20s 故障瞬间、数据检查器、因果证据链接和三组对照。

**再做的三件**：

4. 实现静态站点 MVP：单例故障、共享时钟、不可变 Run、五视图。
5. 打通数据导出/重载、质量门禁、端到端演示与一键数值复核。
6. 完成开源发布审查和第一个可分享的 Demo；再根据用户反馈决定是否扩充故障、Py/Simulink/FMU 与 Agent 竞技。

### 产品角度的最终建议

**FaultLab 的首版价值不是“能模拟很多种故障”，而是“用一个真实可算、完整可查的故障实验，让人理解传感器故障与控制响应的区别”。** 如果 G0 证明这一定位有吸引力，才值得投入后续复杂建模和 Agent Arena。
